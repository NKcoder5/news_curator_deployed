# Check Anything latency, 12–13 October 2026

A Check Anything check took 8–15 s on 11 October and was reported at 25–50 s a
day later. This note records where the time actually went, what was changed,
the measured effect, and the evidence that no verdict changed.

All commands are run from `backend/`.

## Summary

- **Measured, not guessed.** `scripts/profileCheck.js` runs the real check and
  prints a timeline of every stage, evidence channel, model call (provider,
  model, time, or "judgement cache") and HTTP request (with 429/503 retries).
  It can record a check's HTTP traffic and replay it offline, so old and new
  code can be compared on identical evidence and identical latencies.
- **Where the time went.** On a quiet evening the check was already 6–12 s;
  the 25–50 s cases come from conditions the profile exposed: the local model
  being unloaded after five idle minutes (+7 s), NVIDIA NIM answering the
  reference check slowly (5–9 s normally, much longer when busy), Gemini "model
  busy" retries (1 s, 2 s, 4 s on the same model), and Google News answering in
  4–8 s per request on a slow morning. Checks also waited for things they did
  not depend on.
- **What changed.** Message-only checks start before the message is read; the
  claim memory is looked up beside the evidence and written after the answer;
  evidence channels have a 15 s deadline with an honest "could not be read in
  time"; the gateway backs off briefly and jittered and skips a model that asks
  for a long wait; the local model stays loaded for 30 minutes; Wikipedia
  lookups have a timeout; the same message sent again within 20 minutes is
  answered from the check just made.
- **Effect.** On identical replayed evidence: quiet day median 8.4 → 8.3 s,
  slowest 14.1 → 12.0 s; loaded day median 15.0 → 12.0 s, slowest 32.3 → 19.1 s;
  a repeat within 20 minutes 6–15 s → under 0.1 s.
- **Verdicts.** Identical call, rule, per-claim counts and channel outcomes on
  every replayed check (6 of 6, plus the 3 loaded-day checks). One live
  difference (India, 13 Oct morning) is the news itself: the baseline code
  replayed on that morning's evidence gives the same answer.

## How it was measured

```
node scripts/profileCheck.js "India won 84 medals at the Asian Games 2026"
node scripts/profileCheck.js --record run.rec.json --trigger user "msg" ...   # live, keep the HTTP traffic
node scripts/profileCheck.js --replay run.rec.json --trigger user "msg" ...   # offline, same latencies
node scripts/profileCheck.js --replay run.rec.json --busy generativelanguage \
  --slow integrate.api.nvidia.com=4 --slow localhost=+3000 "msg" ...          # a loaded day
```

The profiler writes the claim memory to a throwaway copy of it (copied, then
dropped), so the shared database is only read. The baseline for replays is
commit `0943066` (the last commit before this work), extracted to a scratch
directory with the same profiler.

Live checks used: 12 of the 14 allowed (2 smoke, 4 before, 3 + 3 after; the
cached repeats spend nothing). Messages: "India won 84 medals at the Asian
Games 2026", "TVK won the 2026 bye elections", "Coimbatore district police
seized drugs, gutkha and weapons in a special drive". "RBI has banned 500
rupee notes from tomorrow" is read as a prediction and refused in about 3 s,
so it says nothing about the evidence channels and was not repeated.

## Where the time went (before, live, 12 Oct afternoon)

Times are seconds from the start of the check to the end of each stage.

| Message | Total | Understanding | Writing checks done | Reference check done | News search done | This week done | Fact-checks done | Claim memory |
|---|---|---|---|---|---|---|---|---|
| India 84 medals | 12.0 | 3.1 | 8.6 | **11.9** | 7.9 | 7.4 | 6.3 | 0.1 |
| TVK bye elections | 6.7 | 1.5 | **6.6** | – | 6.0 | 6.1 | 3.9 | 0.0 |
| Coimbatore seizure | 7.2 | 2.6 | **7.1** | – | 5.6 | 3.5 | 5.0 | 0.0 |
| India, repeated (judgement cache) | 6.2 | 0.0 | 4.8 | **6.1** | 0.0 | 0.0 | 0.0 | 0.0 |

What the profile showed:

1. **Checks waited for what they did not need.** The four writing checks and
   the reference check read only the message, but started after the
   input-understanding call (1.5–3.1 s). The writing checks queue on the one
   local GPU (about 1.4 s each, 5.5 s together) and the reference check goes to
   NIM (5–9 s), so they landed last. On a repeat, with every Gemini judgement
   cached, the reference check alone held the answer for 6 s: it is not
   temperature 0, so it is never cached.
2. **The local model unloads after five idle minutes.** The first two writing
   checks after a pause took 8.3 s and 9.5 s against 1.4–2.8 s warm.
3. **The claim memory sat between the verdict and the reader.** Measured at
   0.0–0.1 s here (local MongoDB, ten records, no ambiguous match), but filing
   an ambiguous claim asks a model up to three times in a row (1.5–3 s each).
4. **Retries were long and in step.** A 429 or 503 cost 1 s, 2 s and 4 s on
   the same model before the next was tried; Gemini's per-minute limit names
   the rest of the minute, so those retries mostly failed again.
5. **No timeout on Wikipedia** (both requests behind the reference check) or on
   the feed's NewsAPI request.
6. **The network sets the floor.** On 13 Oct morning Google News answered in
   3.8–7.9 s per request; news search and this week's coverage each took about
   11 s after the claims were known, in both versions.
7. **Already fine:** the stance judgement is one call per claim over all its
   headlines (nothing to batch); a single check fits in the gateway's
   concurrency (Gemini 6, NIM 2, Ollama 2); news fetches had timeouts.

### The deadline, and why a missing channel moves no verdict

A reader's check gives the evidence channels 15 s from when they start (the
slowest measured landed at 8.8 s; a busy provider has held a check for
25–50 s). A channel still out is reported on the page as "could not be read in
time", and its value is the shape the verdict engine already reads as "did not
run": the news search as `error` (so the rules say they could not check,
never "nobody reports this"), a writing check with no score (never 0, which
would read as "names no sources"), no ruling, no coverage, no reference
finding. `test/channelDeadline.test.js` holds each one, over 648 evidence
combinations, to deciding exactly as a channel that ran and found nothing;
for the news search, to the same answer or CANNOT VERIFY. The work itself is
not cancelled, only no longer waited for.

### The minutes-ago answer

Twenty minutes, because claims about "now" are time-sensitive. Only for the
identical message (same text up to spacing, source, link and kind): the
stored report quotes the message (its first line, the sentences the writing
checks flagged, its English reading) and must never be shown to someone who
did not send it, and the writing checks, which can decide a verdict (rule R7),
read the wording; capitals are a different message. Served only while the
claim records still point at that check (no re-check, no later check of the
claim) and the verdict engine is unchanged; only to readers (`trigger:
'user'`), never to evaluation runs or re-checks; only from a check with every
channel read. The result carries `cached: true`, `checkedAt` and
`ageSeconds`, and the repeat is counted in the record's `timesSeen`.

### Against the target

The target was a median of at most 12 s and a 95th percentile of at most 20 s
on a warm process. Met on the 12 Oct evidence (median 8.3 s) and on the
loaded-day replay (median 12.0 s, slowest 19.1 s), where the deadline is what
holds the tail: 15 s for the evidence after the message is read, so a check
whose understanding call is normal answers within about 18 s whatever a
provider does. Not met on the 13 Oct morning evidence (median 13.6 s): there
the news searches themselves took 11 s, the same in both versions, and a
shorter deadline would have traded correct answers for speed.

## Verdicts unchanged: the evidence

- **Replays.** On both recordings, old and new code produced identical
  verdict objects: call, rule, per-claim support and contradiction counts,
  fact-check, this-week and reference outcomes, writing scores (6 of 6). On
  the loaded-day replay the calls and rules are identical too; the new code
  reported India's reference check as not read in time, which the news
  contradiction decides regardless.
- **Live.** Calls and rules matched before and after on all three messages on
  12 Oct (contradicting outlets for India 4 → 2 and supporting outlets for TVK
  6 → 7: the news moved between runs). On 13 Oct morning India came back
  CANNOT VERIFY: that morning's Google News results no longer carried the
  "85 medals" reports among their top results (the competing-figure probe
  searched "20 medals" instead), and the baseline code replayed on that
  morning's recording gives the same CANNOT VERIFY.
- **Deterministic tests.** `test/channelDeadline.test.js` (unread channels
  decide as absent; the deadline, the early start and its fall-back for other
  languages end to end), `test/claimMemoryDeferred.test.js` (the page is told
  exactly what the write stores; nothing stored before the write; a record
  created meanwhile is joined; `recordCheck` in one call stores the same as
  lookup and write apart), `test/contentCheckLatency.test.js` (what the answer
  waits for, the cache's conditions, evaluation checks and re-checks always
  run in full), `test/gatewayBackoff.test.js`.

## Not done, and for whoever merges

- Not changed, on purpose: prompts, verdict rules, routing. The reference
  check stays on NIM and at its own temperature; moving it to Gemini or to
  temperature 0 would make it faster and cacheable but could change verdicts.
- Possible next steps: search Google News with the full and the shortened
  query together (one round trip less when the full query finds too few
  outlets); for messages with two claims, read the second claim's week in
  advance (costs quota); hedge a slow NIM reference check to Gemini.
- New report fields: `unreadChannels` (and `unread`/`standDownReason` on the
  affected factors and channel events), and on a minutes-ago answer `cached:
  true`, `checkedAt`, `ageSeconds`, with a `cached` stage event. The frontend
  can show these; `docs/api/openapi.json` does not describe them yet.
- New optional variable: `OLLAMA_KEEP_ALIVE` (default `30m`).
- Scripts that exit straight after their last check should
  `await recordsSettled()` from `services/contentCheck.js` first, or the last
  claim-memory write may be cut off.
