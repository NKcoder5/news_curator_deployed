# Own models, phase A: a pair classifier that does not call an external API

14 October 2026. Engineering note for the own-models stream. Code: `ml/` (training, evaluation, export) and
`backend/services/localNli.js` (inference in Node). Reproduction: `ml/README.md`.

## Summary

* One small multilingual model reads a **premise** (a headline, a fact-check headline, an encyclopedia sentence) and a
  **claim** and answers *entailment*, *neutral* or *contradiction*. It is the building block for the jobs the pipeline now
  pays an external LLM for: headline stance, relevance, fact-check claim matching, claim matching of ambiguous pairs,
  the Wikipedia premise check and this week's coverage. **Nothing is wired into verdicts yet**, as agreed.
* Base model kept: `MoritzLaurer/multilingual-MiniLMv2-L12-mnli-xnli` (118M parameters), fine-tuned for 9.7 minutes on 186,266
  pairs. Exported with a pruned vocabulary and int8 weights it is **43 MB on disk, 7 ms per pair on one CPU thread, and +143 MB of
  resident memory in Node** (the unpruned export would have been 113 MB on disk and +421 MB in memory).
* Against the same base model used zero-shot, the false-contradiction rate (a pair that is not a contradiction called one,
  the error that turns a true claim into FAKE) falls from 29% to 12.5% on our hand-written blind pairs, from 47% to 10% on the
  project's claim-matching pairs, from 33% to 1% on FNC-1 headline stance, and on the held-out synthetic frames from 21% to 9%.
  On public NLI sets in Hindi and Tamil it is no better than the base (13 to 16% against 13%) and needs a stricter threshold to improve (below).
* It is **not yet good enough to replace the LLM everywhere**. It is good for relevance and for deciding whether two claims are
  the same claim, plausible for the encyclopedia premise check with a strict threshold, and not good enough for agree/disagree
  stance (it misses reversed outcomes written in new words). Section "What it can replace" gives the task-by-task view.
* The mDeBERTa comparison was **not completed**: its fine-tune would have taken about 7.6 hours on this GPU against a 12:15 deadline,
  and the lead stopped it. The zero-shot mDeBERTa numbers stand as the reference for what a larger model could reach.

## Data

Labels are 0 entailment, 1 neutral, 2 contradiction. Premise = evidence, hypothesis = the claim being judged.

| source | pairs in training | what it contributes |
|---|---:|---|
| synthetic, generated by `ml/src/synth.py` | 90,000 | the failure modes below, in English, Hindi and Tamil |
| FEVER-NLI (Nie et al.; the Hub copy has its columns swapped, fixed) | 23,800 | claim against encyclopedia evidence |
| FNC-1 stance (headline vs best-matching body sentences) | 20,470 | agree / disagree / discuss / unrelated mapped to entail / contradict / neutral / neutral |
| MultiNLI | 18,000 | replay, so general English NLI is not forgotten |
| IndicXNLI Tamil / Hindi | 15,999 / 7,998 | Tamil and Hindi NLI |

Not used for training, evaluation only: FNC-1's official test set (7,600 sampled: all 1,903 agree and 697 disagree, 2,500 discuss, 2,500
unrelated), XNLI Hindi test (5,010), IndicXNLI Tamil test (5,010) and Hindi test (2,400), FEVER-NLI dev (2,136), MultiNLI matched
validation (2,400).

**The synthetic set.** One generator per failure mode, each producing entailment, contradiction or neutral pairs with the premise
dressed like real input (a " - Publisher" tail, datelines, "officials said"):

| debunk | "Video of X dancing is AI-generated" vs "A video shows X dancing"; "Fact check: claim ... is false" | contradiction; "verified" entailment; a debunk of something else neutral |
| same_entity | one person or organisation, a different event | neutral |
| sibling_event | the Dharapuram bypoll vs the Madurantakam bypoll: same subject and verb, another named event | neutral |
| swapped_actor | one seat, one winner: another party named as the winner | contradiction |
| number_format | 5.5% = 5.50 per cent, Rs 2,000 = 2000 rupees, Rs 5 lakh = Rs 5,00,000, "six" = 6 | entailment; another figure contradiction |
| paraphrase | passive voice, synonyms, abbreviations, ordinals ("2nd" = "second") | entailment |
| unsupported | the claim adds a detail the premise does not give ("died" vs "died in Goa") | neutral |
| encyclopedic | an entry that states, omits or contradicts a death place, birth place, year, award, office, capital | entailment / neutral / contradiction (never contradiction for silence) |
| multilingual | Hindi and Tamil headlines against English or same-language claims | all three |

**Split by claim.** Test pairs use people, teams, places and organisations that no training pair uses (every fifth item of each pool is
reserved). Fifteen sentence frames are held out of training altogether and form the "unseen frames" test; claims that appear in both are
dropped from the test set. Names of private persons are fictional.

**Two honest caveats about the evaluation sets.**

1. The project's claim-matching suites (`backend/eval/suites/claim_matching*.json`, 80 pairs, scored in both directions: `same` is
   entailment, `variant` contradiction, `different` neutral) were never trained on, but the first error analysis of a fine-tuned model
   on them (two sibling events called contradictions, a swapped party called an entailment, "5.5%" vs "5.50%" called a contradiction)
   decided which generators to add. They are therefore a *development* set for this model, not a blind one. Frames that copied
   specific pairs of those suites were deliberately left out.
2. `ml/eval/blind_pairs.json` is the blind check: 72 hand-written pairs (24 per label, on topics unlike the suites) written before the last
   round of generator changes and evaluated only once, on the final model. With 72 pairs one pair is 1.4 points and a 95% interval is
   about +/-9 points, so read it as a sanity check, not a measurement of fine differences.

## Base model: decision

Zero-shot comparison of the three candidates (accuracy %, and false-contradiction % in brackets):

| set | MiniLM-L6 | MiniLM-L12 | mDeBERTa-v3-base |
|---|---:|---:|---:|
| synthetic, unseen frames | 71.0 (26.8) | 78.7 (20.7) | 81.5 (17.3) |
| claim-matching suites | 55.6 (48.3) | 59.4 (46.7) | 77.5 (20.8) |
| blind pairs | 63.9 (35.4) | 68.1 (29.2) | 87.5 (12.5) |
| FNC-1 | 37.9 (39.8) | 42.0 (33.0) | 52.2 (14.5) |
| XNLI Hindi | 69.1 (14.1) | 72.3 (13.3) | 76.9 (8.0) |
| IndicXNLI Tamil | 69.6 (11.8) | 72.2 (12.6) | 75.6 (6.3) |
| int8 ONNX size without pruning | about 107 MB (estimated) | 113 MB (measured) | about 280 MB (estimated) |

mDeBERTa is clearly the stronger starting point, by 8 to 20 points on our domain. It was still not taken, for three reasons that
are measured rather than assumed:

* **Size.** Unpruned it does not fit the 150 MB budget (about 280 MB int8). With the vocabulary cut to the 49,765 pieces our text uses,
  its int8 export measured 123 MB on the zero-shot weights (after folding the Identity nodes DeBERTa's shared projection leaves in the
  graph, which otherwise keep 24 matrices in fp32 and add 54 MB). Its 12-layer, 768-wide encoder is about four times MiniLM's; the CPU
  latency was not measured.
* **Training cost on this GPU.** The fine-tune did not complete. A first attempt silently trained in fp16 weights (the Hub checkpoint is
  stored in fp16 and transformers 5 loads it as stored; fixed with `dtype=torch.float32` in `train.py`, `evaluate.py`, `export_onnx.py`).
  The second, with fp32 weights, a frozen 192M-parameter embedding table and bf16 autocast, ran at 1.2 seconds per step because the 8 GB
  card was full and spilling about 1.8 GB into shared memory: 11,642 steps would have taken about 7.6 hours. It was stopped at step 400
  (loss 0.32); its log is in `ml/artifacts/train_mdeberta.log` (not in git). A batch size of 16 or a shorter epoch would probably have
  fixed the memory pressure; it was not tried.
* **Deployment.** The server has 512 MB and no GPU. MiniLM-L12's whole footprint in Node is 145 MB over a 33 MB baseline.

So the decision is MiniLM-L12 on a deployment argument, with the evidence that **a stronger model exists**: zero-shot mDeBERTa is
better than our fine-tuned MiniLM on the blind pairs (87.5% against 80.6%) and on every public NLI set (not FNC-1), and worse on the
in-domain synthetic set, which it was never trained on. A fine-tuned, vocabulary-pruned mDeBERTa is the obvious next candidate if the GPU time exists.

## Training

* Base: MiniLM-L12 (`multilingual-MiniLMv2-L12-mnli-xnli`), full fine-tune, 2 epochs, 11,642 steps, batch 32, learning rate 3e-5 with 6%
  warm-up and linear decay, AdamW, weight decay 0.01, max length 160 tokens (the premise is cut, never the claim), bf16 autocast over fp32
  weights, length-grouped batches. 9.7 minutes on the RTX 5050 Laptop GPU, peak 2.5 GB.
  (bf16 rather than fp16: no loss scaling, and no overflow risk in DeBERTa-style attention if the base is changed later.)
* Three rounds. The same model scored, on the claim-matching pairs, 59.4% zero-shot, 84.4% after round 1 (public data plus the first
  generators), 90.6% after round 2 (sibling events, swapped actors, number formats added) and 90.0% after round 3 (the frames that
  copied suite pairs removed, ordinals and thousands separators added). The blind pairs were evaluated once, on round 3.
* One seed, no hyper-parameter search, no confidence intervals other than the sample-size remark above.

Reading the tables.

* In-domain the gain is large and honest where it is measured on unseen entities and frames: unseen-frame synthetic accuracy 78.7 to
  90.6 (L12), claim pairs 59.4 to 90.0, blind pairs 68.1 to 80.6, FNC-1 42.0 to 77.5. The seen-frames synthetic set (99.8%) only shows that
  the model learned its training distribution.
* On public NLI data (MultiNLI, XNLI Hindi, IndicXNLI, FEVER) it is level with or a little below the zero-shot base (for example XNLI
  Hindi 72.3 to 70.5, MultiNLI 81.4 to 79.8): about half of the training mix is synthetic and another tenth headline stance, so some general NLI is traded away. The false-contradiction
  rate there is about 13 to 15% in both, and the strict threshold cuts it to 2 to 3% at the cost of contradiction recall (77% to 47% on XNLI Hindi).
* FNC-1 disagree is the weak spot: recall 14.5% (the body excerpt rarely states the denial in the sentences our overlap picks). The same

## Export, quantisation and speed

* `ml/src/export_onnx.py`: the fine-tuned model is exported with the legacy TorchScript exporter (opset 17, dynamic batch and sequence),
  then quantised with ONNX Runtime's dynamic quantiser: int8 weights for every MatMul and for the embedding table, activations quantised at
  run time.
* **Per-channel scales are needed.** The first export used one scale per matrix and lost accuracy (synthetic seen frames 99.8 to 97.4, claim pairs
  90.0 to 85.0, blind 80.6 to 79.2; unseen frames went the other way, 90.6 to 92.0). With per-channel scales the int8 model matches fp32 within
  0.8 points of accuracy on every set (tables above; the false-contradiction rate is within 1.5 points everywhere).
* **Vocabulary pruning.** A 250,002-piece vocabulary was cut to 51,170 pieces: those the tokenizer uses on all of the project's text,
  every single-character piece, and the special tokens. Tokenizer and embedding table are renumbered together. Effect: the model file goes
  from 113 MB to 40 MB (the fp32 ONNX from 448 MB to 157 MB) and, more important, Node's resident memory from 454 MB to 176 MB, because
  `@huggingface/tokenizers` holds every piece as a JavaScript object (tokenizer +270 MB and session +146 MB for the full vocabulary; +65 MB and +73 MB pruned). Accuracy is
  unchanged (identical to the unpruned int8 model on all sets). Words the data never used are spelled with smaller kept pieces.
* **Tokenizer parity.** JavaScript and Python tokenisation of 900 test pairs (English, Hindi, Tamil) were identical in 899 cases; the one
  difference is a Hindi sentence of the same length with one different piece. Not a concern at this rate, but it is why the Node test uses
  the real model.

| | value |
|---|---|
| files shipped (`ml/artifacts/minilm-l12-onnx-int8`) | 43.5 MB: `onnx/model_quantized.onnx` 40 MB, `tokenizer.json` 3.4 MB, two small configs |
| ONNX Runtime on CPU, Python, 1 thread | 7.2 ms median, 10.2 ms p95 per pair; 6.0 ms per pair in batches of 16 |

Machine: a 28-thread laptop CPU with other work running; a small cloud vCPU will be slower, perhaps two to three times.

## The Node service

`backend/services/localNli.js`: `judgePair(premise, hypothesis)` resolves `{ label, scores: { entailment, neutral, contradiction } }`,
`judgePairs(pairs)` does the same for an array (batches of 16, sorted by length). It returns `null` for a pair, and for every pair, when the
model directory is absent or broken, `onnxruntime-node` or `@huggingface/tokenizers` is not installed, the text is empty, or inference
throws: it never throws, so a caller keeps its previous path. Environment: `LOCAL_NLI_MODEL_DIR` (default `ml/artifacts/minilm-l12-onnx-int8`
next to `backend/`), `LOCAL_NLI_THREADS` (default 2). The label order is read from the model's `config.json`. Both packages are loaded on
first use, so requiring the service costs nothing. `backend/test/localNli.test.js`: six tests that run everywhere (absent and broken model,
label order, softmax, padding, truncation) and one that runs the real model when installed and skips otherwise; it checks that an
encyclopedia entry giving only a death date is not a contradiction of "died in Goa", the case where a fallback LLM called three true claims
FAKE on 13 October.

## Risks and things to know

* **Model files are not in git** (`ml/artifacts/` is ignored). The server needs the 43 MB directory copied to it and
  `LOCAL_NLI_MODEL_DIR` set; without it the service answers null and nothing changes.
* **New backend dependencies**: `onnxruntime-node` 1.30.0 (about 300 MB unpacked on disk, all platforms) and `@huggingface/tokenizers` 0.2.0
  (360 KB). `package.json` and `package-lock.json` are updated; `npm ci` is needed after merging. `npm` warns that the `onnxruntime-node`
  install script has not been approved; the CPU binaries for Windows, Linux and macOS are bundled in the package, the script only fetches
  optional GPU libraries.
* **`backend/Dockerfile` uses `node:24-alpine` (musl). `onnxruntime-node` ships glibc binaries**, so the model will not load there (the
  service logs one warning and returns null). Use a glibc base such as `node:24-slim` before deploying the model in that image. Render's
  native Node runtime is glibc.
* The prebuilt-binary loader runs inside the API process; a pathological input cannot crash it (errors are caught per batch), but the
  first call parses the 3.4 MB tokenizer on the event loop (327 ms in all, measured, including creating the session).
* The model reads text it is given as data. Nothing in it follows instructions, but a premise that is attacker-controlled can of course
  push its answer; the existing fencing and the independence logic still apply upstream.
* Synthetic data teaches templates. The unseen-frame numbers show how far that generalises (about 90%), the blind numbers how far it
  generalises to hand-written text (about 80%); expect real headlines to behave like the blind set.
